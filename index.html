ASIO Timer: Sender


struct timer_sender {
  using sender_concept = stdexec::sender_t;

  using completion_signatures =
    stdexec::completion_signatures<
      stdexec::set_value_t(int),
      stdexec::set_error_t(int)>

  auto connect(stdexec::receiver auto rcvr) {
    asio::steady_timer timer(io, asio::chrono::seconds(n_secs));

    std::printf("Created %d second timer\n", n_secs);

    return timer_op {
      io, n_secs, std::move(timer), std::move(rcvr)
    };
  };

  asio::io_context& io;
  int n_secs;
};
This is a sender. Senders describe asynchronous operations or work, but they don't trigger it. So, declaring a sender is like declaring a callable so a function or a lambda. This is beneficial because it allows you to create arbitraily complex task graphs, so multiple senders composed together with adaptors, before actually scheduling the execution on a resource.

This line declares this type as a sender.

This line declares how the sender can complete, and this is done with a list of callbacks. In this case, we are declaring that the sender can complete sucessfully, in which case we return an int, and also it can complete in error (also with an int). There is a third callback type declared with another function type called set_stopped_t, which signals that the operation completed without suceeding or failing. This result is used to indicate that the operation stopped early typically becuase the result is no longer needed.

This is the connect member function. Connect takes a "receiver" and returns an operation state, which is the result of connecting a sender and a receiver together.

In this case, connect is called by stdexec when we start the operation and stdexec is responsible for ensuring that the opertion state does not move and remains valid during the lifetime of the asynchronous operation.

ASIO Timer: Receiver


template <class Receiver>
struct timer_op {
  asio::io_context& io;
  int n_secs;
  asio::steady_timer timer;
  Receiver rcvr;

  static void callback(const boost::system::error_code& error,
    int n_secs, Receiver& rcvr)
  {
    std::printf("Finished %d second timer\n", n_secs);

    if (error != boost::system::errc::success)
      stdexec::set_error(std::move(rcvr), error);
    else
      stdexec::set_value(std::move(rcvr), 0);
  }

  void start() noexcept
  {
    timer.async_wait(
      boost::bind(callback, boost::asio::placeholders::error,
      n_secs, rcvr)
    );

    io.run();
  }
};
Receivers represent the continuation of an asynchronous operation and this is where the three callbacks are demultiplexed.

Start is where the asynchronous operation is actually triggerred and it is at this point where the operation state is required to not move.

ASIO Timer: Main Code


timer_sender async_timer(asio::io_context& io, int n_secs) {
  return {io, n_secs};
}

int main() {
  asio::io_context io;

  auto task_timer = async_timer(io, 5);
  auto print_ret_val = stdexec::then(task_timer, [](int n)
  {
    std::printf("Return value: %d\n", n);
  });

  stdexec::sync_wait(print_ret_val);
}
And then finally 'sync_wait', which is a sender consumer (i.e. an algorithm that takes a sender but does not return one) and blocks the current thread until the sender returns its result.

Adaptors

  • Algorithms for common asynchronous patterns
    •
    • then: input sender → function
      •
    • continues_on: change execution resource
      •
    • bulk: runs a task for every index in a space
      •
  • Most adaptors are pipeable: |
    •
  • cppreference and std::exec have good examples
    •
Async. algorithms for common asynchronous patterns

Sender adaptors are functions that return parent senders from one or more child senders plus a (possiby empty) set of additional arguments.

  • then is a chaining operation
  • continues_on moves a sender onto a different scheduler (execution resource)
  • bulk takes an input sender, a integral and a callable, and then calls that callable for each index in a range along with the values produced by the input sender. So you might have a sender that calculates a coefficient and then you could use bulk to adapt that sender into a sender that performs a calculation on each value stored in a vector, using that coefficient as input.

When I say 'pipeable', is that the Bitwise OR operator is overloaded for the purpose of creating sender chains.

Coroutines

  • Senders and Receivers work well with coroutines
    •
  • All awaitables are senders
    •
  • task<> type in std::exec knows how to await senders
    •
  • You can co_await without having to do extra work
    •
  • More information in key references
    •
If you have an awaitable i.e. a coroutine type then with minimal modifications you can use this in place of a sender. Similarly, std:exec has a task type that knows how to await senders. So, you can mix-and-match senders and coroutines as required.
